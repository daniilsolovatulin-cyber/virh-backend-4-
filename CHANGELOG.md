## 0. Что добавлено в этой итерации

### 0.1. Лимит Groq больше не обрывает генерацию («3/3» → ждём сколько нужно)
**Было:** при 429 генерация делала 3–4 попытки и падала с ошибкой; в статусе мелькало «жду 1/3… 3/3».
**Стало:** лимит — это пауза, а не ошибка. Ключи перебираются по кругу, между кругами растущая
пауза (4 → 8 → 12 с, максимум 60 с) с обратным отсчётом в статусе, и так **до успеха**.
Выход — только успешный ответ или кнопка **«Отменить»** на экране генерации
(реальная ошибка сети или 5xx по-прежнему показывается сразу, чтобы не ждать вечно впустую).
`public/app.js`

### 0.2. Таймер сверху: сколько прошло и сколько осталось
На экране генерации появилась верхняя строка: **прошло** (`0:00`, тикает каждые полсекунды),
**осталось ≈** (оценка по скорости уже сгенерированных вопросов) и кнопка «Отменить».
Пока действует лимит, вместо «осталось» идёт обратный отсчёт паузы.
В лобби комнаты, пока хост генерирует вопросы, показывается «Прошло 0:12 · обычно 10–30 секунд».
`public/app.js`, `public/styles.css`

### 0.3. Данные и подсказки размыты, пока ИИ ищет
Пока идёт генерация, ниже индикатора показывается будущий экран в размытии
(`filter: blur(5px)`): карточка вопроса, подсказка темы и варианты ответов видны,
но прочитать их нельзя. Работает на экране генерации, в лобби комнаты и при ожидании первого вопроса.
`public/app.js`, `public/styles.css`

### 0.4. Переходы между экранами без мелькания
**Было:** при смене экрана контент подменялся мгновенно, а шапка пересоздавалась на **каждый** `render()` —
значит, заново создавались аватар и иконки, отсюда и вспышка. В CSS при этом лежали отключённая
анимация (`.view { animation: none; }`), неиспользуемый `@keyframes viewIn` и мёртвый класс
`#appMain.leaving`.

**Стало:**
- шапка перерисовывается только при реальном изменении её разметки (сравнение строки);
- переход делает **View Transitions API** — страница целиком уезжает и приезжает без вспышки,
  направление зависит от глубины экрана (`data-nav="forward|back"`: вперёд — влево, назад — вправо);
- для браузеров без View Transitions — запасная анимация `#appMain.page-in`;
- мёртвый код анимаций удалён, для `prefers-reduced-motion` переходы отключаются полностью.

`public/app.js`, `public/styles.css`

### 0.5. Управление
- **Выход из одиночной викторины** прямо с экрана (раньше — только иконка «на главную» в шапке).
- **Уход с экрана генерации отменяет её**: раньше генерация продолжалась в фоне и потом
  сама перебрасывала пользователя на экран викторины, куда он не собирался.
- **Esc** закрывает и модалку оформления (модалка выхода из комнаты закрывалась и раньше).
- **Ответы с клавиатуры**: `1–4` или `A–D` в одиночной игре и в комнате.
- **Enter** в поле имени профиля сохраняет имя.

`public/app.js`

### 0.6. Компактность
Общий блок размытого предпросмотра `genPreviewHTML()` вместо трёх копий разметки,
один тайкер на все таймеры, уменьшены отступы экрана генерации,
сетка вариантов ответа в превью — в две колонки (`.answers-grid.compact`).

## 1. Критичное

### 1.1. Сервер целиком падал с нативной ошибкой (лучше-sqlite3 11 + Node 24)
**Было:** `node index.js` примерно в половине запусков умирал сразу или через несколько секунд:

```
Assertion failed: (env) != nullptr
Statement::~Statement
```

Воспроизведено на чистом `better-sqlite3` **без кода проекта** → это несовместимость версии 11.x с Node 24,
а не ошибка в логике. В `package.json` стояло `"better-sqlite3": "^11.3.0"`, при этом Node в проекте никак не зафиксирован.

**Исправлено:** `better-sqlite3` поднят до `^12` (проверено: 6/6 стресс-прогонов без падений),
добавлено поле `engines: { "node": ">=20.0.0" }`.
`server/package.json`

### 1.2. Один битый WebSocket-кадр убивал весь сервер (DoS)
**Было:** в `realtime.js` на сокет не вешался обработчик `'error'`.
`ws` при некорректном кадре эмитит `'error'` на объект сокета, а необработанное событие `'error'`
в Node — это исключение, которое роняет процесс целиком. Достаточно было отправить кадр с выставленным RSV1.

**Исправлено:** добавлен `ws.on('error', ...)` (лог вместо падения).
Проверено тестом: после отправки некорректного кадра `/api/health` продолжает отвечать.
`server/realtime.js`

### 1.3. Секрет JWT по умолчанию был общеизвестной константой
**Было:** `const FALLBACK_SECRET = 'dev_secret_change_me'`. Если `JWT_SECRET` не задан, а `NODE_ENV`
не равен ровно `'production'` (например, на хостинге его просто нет), сервер стартовал с публичным секретом —
любой мог подделать токен входа в чужой аккаунт.

**Исправлено:** фолбэк-константы больше нет. Без `JWT_SECRET` генерируется случайный ключ на процесс
(+ громкое предупреждение в лог); в production по-прежнему отказ стартовать.
`server/auth.js`

### 1.4. Игрок не мог вернуться в идущую игру после перезагрузки страницы
**Было:** `POST /api/rooms/:code/join` отдавал `409 room_already_started`, если игра уже началась —
даже для того, кто в этой комнате уже состоит. Обновил страницу в середине игры → вернуться нельзя,
хотя на сервере запись участника и его счёт живы.

**Исправлено:** участник комнаты возвращается в неё в любом статусе; для посторонних поведение прежнее (`409`).
Проверено тестом: `200` для своего и `409` для чужого.
`server/routes/rooms.js`

## 2. Логика игры

### 2.1. Счёт во время игры не обновлялся вообще
Сервер при каждом `reveal` отдаёт актуальные `scores`, но клиент их игнорировал, а знак счёта рисовался
из `state.roomMembers`, который обновляется только в лобби. Итог: весь матч в шапке висело «0» до финальной таблицы.
**Исправлено:** `reveal.scores` вливаются в `state.roomMembers`. `public/app.js`

### 2.2. Режим «Блиц» в комнатах был чисто косметическим
В комментарии `realtime.js` было написано «blitz uses one global timer instead», но никакой разницы в коде не было:
и классика, и блиц игрались по 20 секунд на вопрос. Режим выбирался в UI и сохранялся в БД, но ни на что не влиял.
**Исправлено:** время вопроса теперь зависит от режима — классика 20 с, блиц 10 с (`QUESTION_SECONDS`).
Проверено тестом: дедлайн ~20 000 мс и ~10 000 мс соответственно. `server/realtime.js`

### 2.3. Ответ принимался после истечения времени
`submitAnswer` не смотрел на дедлайн: если reveal ещё не сработал, ответ после 20-й секунды засчитывался.
**Исправлено:** ответы позже дедлайна +750 мс (запас на сеть) отбрасываются. `server/realtime.js`

### 2.4. Обращение к несуществующему полю `room.age_group`
В БД не было колонки `age_group`, поэтому в генератор вопросов всегда уходило `undefined` и подсказка
про аудиторию молча подменялась на «смешанная». Само по себе не падало, но задуманное поведение не работало.
**Исправлено:** колонка добавлена (и в `CREATE TABLE`, и миграцией `ALTER TABLE` для существующих баз). `server/db/init.js`

### 2.5. Вопрос без валидного `correct` мог попасть в игру
Проверялось только `Number.isInteger(q.correct)` — без диапазона. Модель могла вернуть `correct: 7`
при четырёх вариантах, и такой вопрос невозможно было ответить правильно. На клиенте проверки `correct` не было вообще.
**Исправлено:** валидация 0 ≤ correct < options.length + проверка, что все варианты — непустые строки,
вопросы обрезаются `trim()`. Синхронно на сервере и в одиночном режиме. `server/questionGen.js`, `public/app.js`

### 2.6. Зависший запрос к Groq вешал комнату навсегда
Запрос к Groq шёл без таймаута: при зависании комната оставалась в статусе `generating` и выйти из него было нечем.
**Исправлено:** `AbortSignal.timeout(30s)` + внятная ошибка на пустой ответ модели. `server/questionGen.js`

### 2.7. «Мёртвые» соединения не отключались
Не было ping/pong. Полуразорванное TCP-соединение не вызывает `close`, игрок навсегда остаётся в списке
активных, и `allMembersAnswered` ждёт его до конца вопроса.
**Исправлено:** heartbeat раз в 30 с, мёртвые сокеты `terminate()`. `server/realtime.js`

## 3. Фронтенд

### 3.1. Название лобби всегда терялось при создании комнаты
У поля `roomNameInput` не было обработчика `oninput`, а обработчик кнопки делал `render()` **до** чтения значения
из DOM. То есть значение читалось из только что перерисованного (пустого) поля.
**Исправлено:** значение живёт в `state.roomSetup.name` и читается оттуда. `public/app.js`

### 3.2. Гонка в одиночном блице: экран квиза поверх экрана результата
Если время блица истекало в течение 1.1 с после ответа, `finishQuiz()` показывал результат,
а затем отложенный `setTimeout(nextQuestion)` перерисовывал вопрос заново (и `state.view` при этом оставался `result`).
**Исправлено:** таймер перехода хранится в `state.pendingAdvance`, гасится в `finishQuiz`,
плюс защита `if (state.view !== 'quiz') return`. `public/app.js`

### 3.3. Отсчёт «3-2-1-СТАРТ» дорисовывал игру после выхода из комнаты
Если выйти из комнаты во время отсчёта, колбэк всё равно выполнялся и обращался к `state.room.topic`
при `state.room === null` → необработанное исключение.
**Исправлено:** колбэк сверяет сокет и текущий экран, `roomPlayHTML` больше не падает без `state.room`. `public/app.js`

### 3.4. Код комнаты стирался при неудачном входе
Обработчик ошибки вызывал `render()`, а поле кода не было привязано к состоянию — пользователь терял введённый код.
**Исправлено:** `state.roomJoinCode`. `public/app.js`

### 3.5. Выбранный ответ сразу красился красным
По клику кнопка получала класс `wrong` («исправится при reveal, если верно») — до ответа сервера игрок видел
красный крест. **Исправлено:** нейтральный класс `picked` (+ стиль в `styles.css`). `public/app.js`, `public/styles.css`

### 3.6. Повреждённый `localStorage` ронял всё приложение
`JSON.parse(localStorage.getItem('quiz_groq_keys'))` выполнялся на верхнем уровне скрипта: любое мусорное значение —
и не запускался вообще ни один экран. То же в `sound.js` с настройками звука.
**Исправлено:** безопасный разбор с фолбэком. `public/app.js`, `public/sound.js`

### 3.7. Прочее по мелочи
- `state.myLastAnswerIdx` использовался, но не был объявлен и не сбрасывался между вопросами — добавлен и сбрасывается.
- Таймер в игре был жёстко подписан «20с»; теперь считает от реального дедлайна с сервера.
- Дублирующийся расчёт класса кнопки ответа (одна копия была мёртвым кодом) сведён к одному месту.
- `logout()` не выходил из комнаты — оставался висеть сокет и состояние комнаты.
- Цвет аватара подставлялся в `style` без проверки — теперь только валидный hex.
- Дедлайн в комнате считался от `Date.now() + 20000`; заменено на фактический `msg.deadline`.
- `reveal.answers` мог отсутствовать — добавлена проверка.

## 7. Что осталось (сознательно не трогал)

1. **Rate limit и `trust proxy`.** `app.set('trust proxy', 1)` нужен на Render, но если сервер доступен напрямую,
   `X-Forwarded-For` можно подделать и обойти лимитер по IP. Правильное решение — доверять прокси только
   в проде (env-флаг) либо лимитировать ещё и по логину. Поведение не менял, чтобы не сломать работу за прокси.
2. **Снапшоты в Supabase не тестировались** — нужны реальные `SUPABASE_URL`/`SUPABASE_SECRET_KEY`.
   Логика в `db/init.js` при неудачном восстановлении намеренно полностью отключает сохранение (чтобы не затереть бэкап),
   но тогда данные живут только в файле — стоит помнить при деплое без volume.
3. **В репозитории нет lock-файла** (`package-lock.json`, созданный моим `npm install`, удалён как артефакт;
   в проекте при этом объявлен `packageManager: pnpm`). Без lock-файла следующий `npm install`
   снова может подтянуть несовместимую сборку — лучше зафиксировать зависимости.
4. ~~Нет автотестов.~~ Добавлены: `npm test` в папке `server` (см. раздел «Как проверялось»).
   Тесты не подключены к CI — если деплой через GitHub, стоит добавить workflow с `npm test`.
5. **`virh-backend.onrender.com` в `public/config.js`** оставлен как есть: в `render.yaml` сервис называется
   `vihr-api`, то есть в адресе возможна опечатка (virh ↔ vihr). Проверь фактический адрес бэкенда.
6. **Реконнект во время reveal.** Если игрок переподключится ровно между reveal и следующим вопросом,
   он увидит вопрос без разбора ответов (сервер не переотправляет последний reveal).
